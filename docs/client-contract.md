# 出图客户端接入契约：断连后的承诺恢复

契约版本 v1 · 2026-11-16 · 适用基线 FormatVersion 1
证据来源：`python3 scripts/reconnect-evidence.py` 对真实服务进程的实际调用输出（本文件引用为 E1–E5），以及 `scripts/walkthrough.py` 各工作流。
评审方式：第 7 节 G 条目是当前保证，版本变更不得破坏，破坏即视为契约变更；F 条目是未来产品建议，不构成保证。R/B 条目是建立在这些保证上的客户端行为规范与交互边界。

## 1. 问题

接入方提交出图任务后，一次连接中断（响应丢失、进程重启、网络闪断）让客户端失去任务句柄。恢复时只有两种选择：

- **选择 A：继续原来的画面承诺**——用同一幂等键重放、等待或重试同一个任务。
- **选择 B：允许用户发起一次新的创作输出**——换键、重新冻结快照、提交新任务。

本契约沿当前快照、任务与结果的关系推导两种选择的后果，回答：用户修改场景或撤回快照后，客户端还能对哪一张图作出承诺。

## 2. 事实基础：快照、任务、结果、收据的关系

以下事实来自当前实现，是全部推导的前提：

| 事实 | 位置 |
|---|---|
| 冻结在同一次状态提交中捕获场景修订与全部引用素材字节；快照摘要覆盖文档和素材闭包，不覆盖撤回状态 | `internal/service/scenes.go:69`、`internal/model/types.go:137` |
| 任务接受时把整个快照复制进 `Job.Payload`，执行器只渲染 Payload，不读取当前场景、素材或快照记录 | `internal/service/jobs.go:45`、`internal/engine/worker.go:110` |
| 幂等收据的请求语义为快照 ID 和输出倍数；命中收据直接返回原任务，不再检查快照状态；收据不随任务终态、快照撤回、结果清理或进程重启失效 | `internal/service/jobs.go:16-24`、`docs/api.md` |
| 撤回只翻转快照状态，不触碰任何任务 | `internal/service/scenes.go:95` |
| 重试仅接受 failed/cancelled，attempt 增加且沿用固定输入，不检查快照状态；succeeded 不能重试 | `internal/service/jobs.go:76` |
| 进程恢复把 running 重新入队，不增加 attempt，内容不变 | `internal/engine/worker.go:25` |
| 清理结果只删除 PNG 字节，保留任务成功事实与摘要 | `internal/service/jobs.go:106` |
| 同一固定输入的两次渲染像素零差异（确定性渲染） | walkthrough `compare-renders`、证据 E2 |

由此得出本契约的核心区分：**断连是传输层事件，不改变任何承诺的内容；改变承诺内容的是人的操作——修改场景（revision 前进）与撤回快照（state 翻转）。** 客户端可以自动处理前者，无权替用户决定后者。

## 3. 两种选择的后果推导

**选择 A（继续原承诺）**
- 同一幂等键重放返回同一个任务，一个键至多一次出图，不产生重复（证据 E1）。
- 任务内容在提交时固定，之后修改场景、素材退役、快照撤回都不改变它；客户端最终拿到的就是当初那张图（证据 E3、E5）。
- 代价：若用户在中断期间已经改稿或撤回，继续原承诺等于静默交付旧图。

**选择 B（发起新创作）**
- 同一快照换用新键：产生第二个任务渲染同一内容，占用双份队列槽位、执行时间和结果字节（证据 E2：两份相同像素共 14120 字节）。这是重复出图，不是新创作。
- 重新冻结当前场景再提交：得到真正的新图，但旧任务、旧收据依然存在，客户端必须自行维护"哪个任务对应用户哪次意图"的谱系（证据 E3）。
- 快照已撤回时，新键提交被 409 拒绝；要新图只能先冻结新快照，而是否覆盖用户的撤回意图无法自动判断（证据 E5）。

## 4. 承诺矩阵：修改场景、撤回快照、清理结果之后

客户端持有不同句柄时，能对哪一张图作出承诺：

| 客户端持有 | 场景被修改（revision 前进） | 快照被撤回 | 结果被清理 |
|---|---|---|---|
| 幂等键（收据） | 重放返回原任务，承诺冻结时的图（E1） | 重放仍返回原任务（E5：202） | 重放仍返回原任务（任务事实保留） |
| 任务 queued/running | 继续执行，承诺冻结时的图（E3） | 继续执行到终态（E5） | — |
| 任务 failed/cancelled | 重试仍得冻结时的图 | 重试仍得冻结时的图（E5：attempt 2 成功） | — |
| 任务 succeeded + 结果 live | 承诺冻结时的图，字节可下载 | 同左 | 下载 410；只能承诺成功事实与摘要（E4） |
| 快照 active | 可新提交，承诺该快照的图 | 新提交 409，不能再产生新承诺（E5） | 可用新键重新提交，确定性再生同像素、新结果 ID（E4） |
| 场景当前修订 | 与已冻结的图无关；要新图必须重新冻结 | 场景 active 时可冻结新快照 | — |

客户端**不能**承诺的事：
- 场景修改后，不能凭旧任务承诺新修订的图——新旧两张图都真实存在且不同（E3：43800 个像素不同）。
- 快照撤回后，不能把已接受任务的结果标注为"当前场景"的图。
- 结果清理且快照已撤回后，不能承诺再生该图（新提交 409、成功任务不可重试），只能承诺历史事实。

## 5. 实际调用证据

以下输出由 `scripts/reconnect-evidence.py` 对真实服务进程捕获（2026-11-16，本基线）。

**E1 断连重放。** 提交请求发出后、读取响应前关闭连接；重连用同键同体重放，返回同一个任务 `job-00000003`；同键改 scale=2 返回 `409 {"code":"conflict","error":"idempotency key used for different request"}`。

**E2 换键重复出图。** 同一快照同一缩放换用新键，产生第二个任务 `job-00000006`；事件流中该快照恰有两个排队任务（证明断连请求与重放收敛为一个）；两份结果摘要相同、像素比较 `changedPixels: 0`；单份 7060 字节，状态接口报告结果字节总量 14120——同一内容占双份存储。

**E3 修改场景后的承诺。** 场景改背景色前进到 revision 2 后：快照摘要不变（`9aed87cc…d3d9` 前后一致）；旧任务仍钉在原快照（`snapshotId` 不变）且已成功；新冻结 `snap-00000010` 渲染后与旧结果比较 `changedPixels: 43800`。旧承诺与新图各自独立成立。

**E4 清理后再生。** 清理结果后下载返回 `410 {"code":"gone","error":"artifact png-00000013 was purged"}`；任务保持 `succeeded`；重试成功任务返回 `409 {"code":"conflict","error":"only failed or cancelled jobs can retry"}`；用新键在同一 active 快照重新提交，新任务 `job-00000015` 产出新结果 ID，摘要与被清理结果完全一致。

**E5 撤回快照后的承诺。** 任务取消后撤回快照：新键提交返回 `409 {"code":"conflict","error":"snapshot is revoked"}`；原幂等键重放仍 `202` 返回原任务（状态 cancelled）；撤回的快照仍可读取（`state: revoked`，文档可检视）；对该任务重试返回 `202 attempt: 2` 并最终 `succeeded`，其像素与撤回前同快照渲染结果零差异。事件轨迹：`snapshot.frozen → job.queued → job.running → job.cancelled → snapshot.revoked → job.retried → job.running → job.succeeded`。

## 6. 取舍评审与推荐

| 断连后的客户端策略 | 便利 | 代价与风险 | 证据 |
|---|---|---|---|
| 同键重放 | 找回原任务，一个键至多一次出图 | 无重复；若用户意图已变，交付的是旧图 | E1 |
| 换键重试 | 客户端无需持久化键 | 同一内容重复出图：队列槽位、单执行器时间、结果字节全部翻倍；键冲突时 409 | E2 |
| 重新冻结 + 新任务 | 拿到当前场景的图 | 旧承诺并存需维护谱系；快照撤回后不可用（409） | E3、E5 |
| 自动重试 failed/cancelled | 免交互恢复 | 内容仍是冻结图；场景已改时等于静默交付旧图 | E5 |

结论：**自动重试的便利应当照单全收，但只对"传输失败且意图未变"自动化；重复出图与误用旧图都源于把"人的决定"交给重试逻辑。** 推荐客户端行为：

- R1 每次用户发起的出图分配稳定幂等键并随会话持久化；断连、超时、5xx 后用同键同体重放，绝不换键（E1、E2）。
- R2 重连后先对齐状态再行动：重放取回任务并 `GET /v1/jobs/{id}`，结合 `GET /v1/snapshots/{id}` 与场景 revision 判断承诺是否仍对应用户意图。
- R3 场景 revision 未前进且快照 active 时，可自动等待、下载；429（队列满）退避后同键重放。
- R4 failed/cancelled 的自动重试仅限场景 revision 未前进且快照 active；其余情况进入交互边界（E5）。
- R5 结果 410 后若用户仍要该图且快照 active，可用新键在同一快照重新提交，确定性再生相同像素，并告知用户结果 ID 已变更（E4）。
- R6 同键 409（语义冲突）说明键管理冲突；禁止换键重放，先按 R2 对齐原任务状态（E1、E2）。

**无法自动判断时的交互边界（必须请用户决定）：**

- B1 场景 revision 已前进：旧图与新图都真实存在且不同（E3）。"继续交付旧图"还是"冻结新快照重新出图"是创作意图问题，客户端必须呈现选择，不得静默替换。
- B2 快照已撤回：已接受任务可继续等到成功（E5），但结果不得标注为当前场景的图；不得自动冻结新快照顶替被撤回的内容——撤回是人的意图信号。
- B3 撤回后新键 409：不得自动改键重试同一快照（必然 409），也不得自动改换快照；只能回到 B1/B2 的用户选择。
- B4 结果已清理且快照已撤回：无法再生，只能向用户说明成功事实与摘要仍在（E4、E5）。

## 7. 当前保证与未来产品建议

**当前保证（G，可逐条回归，破坏即契约变更）：**

- G1 同键同语义重放返回同一任务，即使快照已撤回、任务已终态、进程已重启（E1、E5；walkthrough `submit-render`）。
- G2 同键不同语义返回 409（E1）。
- G3 任务内容固定为提交时的快照；之后的场景修改、素材退役、快照撤回均不改变它（E3、E5；walkthrough `freeze-scene`、`retire-asset`）。
- G4 撤回后新键提交返回 409；已接受任务继续执行至终态（E5；walkthrough `revoke-snapshot`）。
- G5 failed/cancelled 可重试，attempt 增加且内容不变；succeeded 不可重试，返回 409（E4、E5；walkthrough `retry-render`）。
- G6 进程重启后 running 任务重新入队，attempt 不变，内容不变（walkthrough `recover-render`）。
- G7 结果清理后下载返回 410，任务成功事实保留；同一 active 快照可用新键重新提交并确定性再生相同像素，结果 ID 更新（E4；walkthrough `purge-artifact`、`compare-renders`）。
- G8 取消与完成竞争同一终态：cancelled 之后不会出现成功结果（walkthrough `cancel-render`）。

**未来产品建议（F，非当前保证，接入方不得依赖）：**

- F1 任务响应携带快照摘要与场景当前 revision 的对照字段，使客户端一次调用识别陈旧（当前需分别读取快照与场景接口）。
- F2 撤回快照时提供级联取消未开始任务的选项（当前撤回不触碰任务，E5）。
- F3 幂等收据的显式作废或过期接口（当前收据永久有效）。
- F4 按请求指纹跨键去重，消除换键导致的重复出图（当前只按键去重，E2）。
- F5 事件游标查询（按 sequence 增量读取），便于重连后对齐（当前返回最近 500 条全量）。
